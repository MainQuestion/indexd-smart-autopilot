# indexd (форк Smart Portfolio): v0.4.1-rc.1

Дата: 27.11.2026. Ветки: `next/indexd-v065` (indexd, `0c5dd34c`), `feat/indexd-ui-econ-e` (web, `faad444a`).
Основа: предыдущая рабочая сборка `v0.6.1-61dc8d0b` (ветка `next/economics-e`) плюс слияние upstream `v0.6.5` (`f823cb5d`, слияние `354ed21d`), правка скрипта сборки (`0c5dd34c`) и исправление карточки хоста в UI (`faad444a`).

**Нумерация.** У форка собственная версия, не привязанная к upstream: приватная сборка `v0.4.1-rc.1-<коммит>`, публичная `v0.4.1-rc.1` (как у renterd). Предыдущий публичный релиз: `v0.4.0-rc.1`.

## Коротко

1. **Слияние с upstream v0.6.5** (v0.6.2–v0.6.5): исправления пополнения счетов приложений на хостах, shared spaces, квоты и лимиты хранения, проверки контрактов, обновления зависимостей.
2. **Доработки Smart Portfolio** (Economics E, новое правило замены контрактов, защита от «залипшего» кандидата, отбор кандидатов по пригодности) входят в эту же сборку без изменений нашей логики.
3. **Исправление в UI:** в карточке хоста «Max Collateral» показывал не лимит залога, а цену залога (поэтому всегда `$0,00`); добавлена отдельная строка «Collateral».
4. **Миграции базы данных есть:** версия схемы PostgreSQL 28 → 32. Откат на прежний exe требует восстановления базы из дампа.

Проверено тестами пакетов `contracts`, `api/admin`, `smart`, `portfolio`, `economics`, `overall`, `risk`, `resources`, `workshare`, `signals`, `client/v2`.

## Что изменилось

### 1. Пополнение счетов приложений на хостах (upstream)

Подтверждено чтением кода и коммитов:

- `077fc040`: занятый контракт больше не увеличивает счётчик подряд идущих неудач пополнения и не ведёт к экспоненциальной паузе. Контракт ждёт до 5 с (`fundLockTimeout`), пулы откладываются на `PoolFundInterval` (5 мин) без штрафа.
- `85994027`: из `HostFundTarget` убрано деление. **При той же настройке `fund_target_bytes` цель пополнения стала вдвое больше**, на каждом хосте в пуле лежит вдвое больше средств. Деньги переходят из остатка уже оплаченного контракта, дополнительно с кошелька ничего не списывается. Чтобы вернуть прежний размер, достаточно уменьшить `fund_target_bytes` вдвое.
- `4284c83d`: метрики пополнения. Аккаунты считаются «готовыми» при пополнении на 30 хостах, поэтому для пула из 5 хостов эти метрики сами по себе не подходят для алерта «счёт опустел».
- `8ad31530`, `067dd1d2`: при обрезке (prune) контракт блокируется на каждую пачку, а не на всё время; `LockContract` принимает контекст. Остальные циклы (закрепление, продление) могут вклиниться.
- **Не изменено upstream:** любая ошибка RPC пополнения (например, при перезапуске hostd) по-прежнему ставит хост на паузу пополнения до 2 часов. Хост по-прежнему читает 4 МиБ сектора до отказа при пустом счёте (`paid_nothing`).

Наблюдение на нашей сети (причина в части **гипотеза**): на одном из хостов 19.11 и 24.11 были эпизоды `not_enough_funds` (3721 событие, 15,44 ГБ отброшенных секторов). 24.11 indexd был выключен 48 минут, 19.11 перед эпизодом перезапускался hostd. Совпадение времени с прерыванием пополнения есть, прямого доказательства причинной связи нет. Практическое правило: не перезапускать hostd и indexd во время крупной заливки.

### 2. Shared spaces и квоты (upstream)

Новые API и таблицы `space_*`, статистика по общим пространствам, фильтр ключей подключения, превысивших квоту, ответ 403 при превышении лимита хранения при закреплении, отклонение объектов с дублями слэбов, проверка размера подписанных URL, эндпоинт «аккаунты, закрепившие объект», проверка полей контракта при формировании/обновлении/продлении, исправления спецификации admin API. **Нашей логикой не используются.**

### 3. Правки при слиянии (наши)

- **Защита от переполнения** перенесена в нашу `exceedsNewContractLimit` (`contracts/placement.go`): стоимость, не помещающаяся в тип, считается превышением лимита, а переполненный лимит недостижим. Раньше при абсурдной цене хоста `Mul64` паниковал. На обычных ценах результат тот же.
- **Блокировка хоста не из таблицы `hosts`**: старые причины блокировки терялись при повторной блокировке. Использован запрос upstream, наша защита от пустых причин сохранена.
- **Открытие чистой upstream-базы**: `runForkTransition` принимал любую БД версии 29–32 без `fork_schema` за старый форк и отказывался открывать. Теперь БД без колонок старого форка не трогается. БД форка (с `fork_schema`) этой ошибке не подвержена.
- Тесты `persist/postgres` ожидают текущую версию списка миграций вместо константы 28 (18 файлов); два теста `api/app` подправлены под новую сигнатуру `NewAPI`.
- `client/v2`: upstream убрал повторную проверку `settings.Prices.Validate(hostKey)`.

### 4. Economics E (`f798c6c4`)

- Цена хранения хоста корректируется **кратностью залога**.
- Якорь шкалы стоимости: **10-й перцентиль** скорректированной полной стоимости (`TotalCost`) среди хостов пула (`InPool`). Хост с ценой не выше якоря получает 10.
- Набор хостов для расчёта: пул плюс хосты, с которыми уже есть контракты.
- Расчёт на Go совпадает с эталоном на Python (125 хостов, погрешность около 1,8·10⁻¹⁵). Формула та же, что в форке renterd.

### 5. Новое правило замены контракта (`a7af841b`)

Старое правило (худший по Smart Overall, порог относительно Economics этого же контракта) делало замену практически невозможной. Новое:

1. **Худший контракт**: статус Good и самая низкая **Economics** (ничья: ниже Smart Overall, затем публичный ключ). Контракт в экономической паузе остаётся худшим в первую очередь.
2. **Кандидат проходит**, если его Economics **строго больше** `Economics худшего × (1 + порог/100)`, его Smart Overall **не ниже** Smart Overall худшего, он не `TooClose` и входит в пул допустимых кандидатов.
3. Из прошедших выбирается наибольший `(Economics + Smart Overall) / 2` (ничья: больше Economics, затем оценка хранилища, затем публичный ключ).
4. Дальше без изменений: `Justified` решает между заменой и экономической паузой.

Настройки: `SmartReplacementThreshold` (по умолчанию 15) относится только к Economics; новых настроек нет. Окно оптимизации прежнее: раз в 4 часа, одна замена за окно. В `smart-autopilot.log` в строки `replace` и `pause` добавлены `candidateSmartOverall` и `selectionScore`.

### 6. Пауза кандидата после неудачного формирования (`9ccc1740`)

- После неудачи по **вине хоста** хост исключается из кандидатов на добавление и замену на **24 часа**, каждая следующая неудача подряд удваивает срок, максимум **7 суток**. Успех сбрасывает запись.
- Не считаются неудачей по вине хоста: нехватка средств в кошельке, ошибки клиентской стороны RPC, отмена, пропуск по условиям, гонка состояний.
- Память паузы **в оперативной памяти**: перезапуск indexd её обнуляет. Работает только в Smart Active. Строка в журнале: `smart candidate cooldown`.

### 7. Отбор кандидатов теми же условиями, что и исполнение (`61dc8d0b`)

Общая функция `contracts.CandidateUnfit`: пригодность хоста, не на Smart-паузе, не заблокирован, разрешён allowlist, версия протокола не ниже минимальной, остаток места не меньше 10 ГБ, цены в допуске. Число `candidates` в журнале станет меньше прежнего.

### 8. Интерфейс и описание API

Подсказки UI под новое правило (`6b3feb9f`), описания в `openapi/components.yml` (`24487d3b`), подсказки по Economics и Smart Overall (`feat/indexd-ui-econ-e`).

### 9. Карточка хоста: Max Collateral (`faad444a`)

В разделе «Pricing & Limits» страницы хостов строка «Max Collateral» брала значение из `settings.prices.collateral` — это **цена залога за байт за блок**, крошечная величина, которая округлялась до `$0,00`. Теперь:

- «Max Collateral» показывает `settings.maxCollateral` — лимит залога хоста **на один контракт** (в SC и в выбранной валюте). По этому лимиту indexd подгоняет размер контракта: при формировании залог берётся как минимум из лимита хоста и максимальной суммы контракта, число секторов считается как лимит ÷ залог за сектор, при продлении и пополнении недостающий залог урезается или операция отклоняется.
- Добавлена строка «Collateral» — **цена залога** за ТБ в месяц, в тех же единицах, что и цена хранения (в таблице хостов такой столбец уже был и был верным).

Проверка: тесты `transform.spec.ts` (два новых, без исправления они падают), `hostsColumns.spec.tsx`, `useHost.spec.tsx`, `hostsLayout.spec.tsx` (49 тестов), `tsc --noEmit` без ошибок. Внешний вид панели в браузере до публикации не проверялся.

## Миграции базы данных

Версия схемы **28 → 32** (четыре миграции upstream, только вперёд): индекс `objects_object_key_idx` по `objects`, таблицы `space_*` со счётчиками и триггерами (`space_objects_maintain_totals`), удаление колонки `account_key`.

- Проверено на БД, созданной сборкой `61dc8d0b` (наша схема и 25 миграций форка): пустая БД 0,52 с, 500 000 объектов 3,5 с (почти всё уходит на индекс по `objects`).
- На рабочей БД (1364 объекта) все четыре миграции прошли за ~0,3 с.
- **Откат только через восстановление дампа:** прежний exe не знает версию схемы 32 (**гипотеза** по коду, на живой БД откат не проверялся).

## Как обновиться

1. Остановить заливку; не перезапускать hostd во время обновления.
2. Сделать дамп БД: `pg_dump -h <хост> -U <пользователь> -d <база> -Fc -f <папка бэкапа>\indexd.dump`. Сохранить `indexd.exe`, `indexd.yml`, каталог данных. **Файлы `consensus.db*` не копировать.**
3. Остановить indexd (и Caddy, если он запускается вместе), заменить `indexd.exe` файлом из архива, запустить как обычно.
4. В `indexd.log` ожидаются сообщения `migration complete` до версии 32 и `node started`; проверить отсутствие записей warn и выше.
5. Через 5–10 минут проверить таблицу `pool_hosts`: у активных хостов `consecutive_failed_funds = 0`, `next_fund` в ближайшие минуты.

Откат: остановить indexd, вернуть прежний exe, восстановить БД (`pg_restore --clean`). Данные, записанные после обновления, при откате теряются.

## Известные особенности

- Лог `smart portfolio` пишется при изменении плана или раз в 30 минут; `optimizationRan` печатается только в строках `decision: none`.
- Экономическая пауза остаётся, пока перенос данных дороже удержания.
- После запуска окно с геоданными на странице Contracts некоторое время «зависает» и затем начинает работать нормально (наблюдалось и раньше; причина не исследована, **гипотеза**: наполнение кэша геоданных).
- В таблице `pool_hosts` остаются старые строки хостов, давно не получающих пополнения. На работу пула не влияют.
- indexd не запускается сам после отключения питания: автозапуск настраивается средствами ОС (на нашей машине это задача планировщика). В релиз не входит.

## Планы

- Короткая пауза пополнения после ошибки RPC (сейчас до 2 часов) и алерт «счёт приложения опустел на хосте». Метрики upstream для пула из 5 хостов не подходят.
- s3d: upstream `v0.3.0` заменил Go-SDK на Rust-обёртку, наши режимы записи (races, noraces, hedge) и клиентское размещение с ним несовместимы. Остаёмся на Go-форке; из upstream `v0.3.0` перенесено слиянием всё, что не требует Rust-SDK. Отдельный релиз s3d `v0.3.1-rc.1`.
