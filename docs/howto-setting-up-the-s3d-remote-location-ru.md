# Настройка удалённой локации IndexD на Windows: от локального запуска до HTTPS

Практический отчёт по настройке удалённой локации IndexD на Windows.
Документ восстановлен по фактически пройденным шагам и наблюдавшимся
результатам: конфигурация IndexD, домен, Caddy, получение
TLS-сертификата, обратное проксирование, авторизация S3D и запуск
локации.

> **О границах инструкции.** Здесь отмечены подтверждённые действия и
> результаты. Некоторые промежуточные команды и полный финальный
> `Caddyfile` не сохранились в доступной истории, поэтому они не
> реконструируются наугад. Секреты DNS-провайдера и ZeroSSL нельзя
> публиковать.

## 1. Схема, к которой пришли

В настройке использовались следующие адреса и порты:

  ----------------------------------------------------------------------------------------
  Компонент               Адрес / порт                             Назначение
  ----------------------- ---------------------------------------- -----------------------
  Публичное имя           `mainask.remotewire.net`                 Домен удалённой локации

  Публичный HTTPS         `https://mainask.remotewire.net:18443`   Адрес, объявляемый для
  endpoint                                                         внешнего подключения

  Caddy                   HTTPS на порту `18443`                   TLS и обратное
                                                                   проксирование

  IndexD application API  `127.0.0.1:19982`                        Локальный upstream для
                                                                   Caddy

  IndexD syncer           `127.0.0.1:19981`                        Локальный syncer

  IndexD admin API        `0.0.0.0:19980`                          Admin API, привязанный
                                                                   ко всем интерфейсам

  PostgreSQL              `127.0.0.1:5432`                         Локальная база данных

  Каталог данных          `D:\IndexD\data\`                        Данные IndexD

  Программа S3D           `C:\S3D\s3d.exe`                         Клиент/процесс
                                                                   удалённой локации
  ----------------------------------------------------------------------------------------

Указанные адреса относятся к конкретной установке. Не копируйте их без
проверки в другой среде. В частности, admin API на `0.0.0.0:19980`
слушает все сетевые интерфейсы --- доступ к нему следует ограничить
средствами конфигурации и сетевой защиты согласно требованиям вашей
установки.

## 2. Проверка локального IndexD до настройки HTTPS

До настройки публичного HTTPS был определён локальный application
endpoint:

``` text
127.0.0.1:19982
```

Проверка корневого URL локального endpoint:

``` powershell
curl.exe -i http://127.0.0.1:19982/
```

**Наблюдавшийся результат:** IndexD возвращал `404` для `/`. Это само по
себе не означало, что сервис не работает: корневой путь не обязан иметь
обработчик. Позже ответ `404` на публичном HTTPS endpoint также
подтвердил, что запрос дошёл до IndexD через Caddy.

Важно отличать: - отказ соединения или тайм-аут --- проблема
доступности, маршрута, порта или процесса; - HTTP-ответ `404` от IndexD
--- соединение установлено, но конкретный путь `/` не найден.

## 3. Конфигурация IndexD

В конфигурации Windows использовались следующие значения:

``` yaml
applicationAPI: 127.0.0.1:19982
adminAPI: 0.0.0.0:19980
syncer: 127.0.0.1:19981
advertiseURL: https://mainask.remotewire.net:18443
data: d:\IndexD\data\
bootstrap: true
network: mainnet
```

Это перечень значений, которые были зафиксированы в ходе настройки, а не
гарантированно полный конфигурационный файл. Названия полей могут
зависеть от версии приложения; сохраняйте исходные обязательные
параметры и проверяйте синтаксис по конфигурации именно вашей версии.

На раннем этапе `advertiseURL` задавался как локальный адрес:

``` yaml
advertiseURL: http://localhost:19982
```

После подготовки публичного HTTPS endpoint его изменили на:

``` yaml
advertiseURL: https://mainask.remotewire.net:18443
```

Идея этого изменения --- объявлять внешний адрес, по которому другие
участники должны обращаться к локации, а не внутренний loopback-адрес
компьютера.

## 4. Домен и DNS

Для публичного endpoint использовалось имя:

``` text
mainask.remotewire.net
```

DNS обслуживался через Dynu. Домен должен указывать на внешний адрес
машины, где принимаются подключения, а Caddy должен иметь возможность
подтвердить контроль над именем при выпуске сертификата.

Перед повторением настройки проверьте: 1. доменное имя разрешается в
актуальный внешний IP; 2. на маршрутизаторе и/или в Windows Firewall
разрешён входящий трафик на выбранный публичный порт; 3. Caddy слушает
именно тот порт, который указан в публичном URL; 4. если применяется DNS
challenge, у Caddy есть соответствующий DNS-провайдер и действительный
API-доступ к Dynu.

Точные DNS-записи, правила маршрутизатора и Windows Firewall в
сохранённой истории не зафиксированы, поэтому здесь они не приводятся
как уже выполненные команды.

## 5. Настройка Caddy как HTTPS reverse proxy

Caddy использовался как HTTPS reverse proxy: принимал запрос на
публичном адресе и передавал его локальному IndexD application API.

Публичный endpoint:

``` text
https://mainask.remotewire.net:18443
```

Локальный upstream:

``` text
127.0.0.1:19982
```

Логика обратного проксирования:

``` caddyfile
https://mainask.remotewire.net:18443 {
    # TLS/issuer и способ DNS challenge должны соответствовать
    # вашей установленной сборке Caddy и настройке Dynu.
    reverse_proxy 127.0.0.1:19982
}
```

Это **схематический фрагмент**, показывающий адрес сайта и upstream, а
не полный финальный `Caddyfile`: конфигурация TLS и DNS-провайдера в
доступной истории полностью не сохранилась. Не заменяйте им рабочий файл
целиком.

В ходе настройки сначала использовался тестовый ответ Caddy:

``` caddyfile
respond "indexD HTTPS endpoint is ready" 200
```

Он позволял проверить HTTPS и маршрут до Caddy отдельно от IndexD. После
этого тестовый `respond` заменили на `reverse_proxy 127.0.0.1:19982`.

## 6. Сложность № 1: ограничение Let's Encrypt

При первой попытке выпуска сертификата через production ACME Let's
Encrypt был получен ответ HTTP `429`.

В сообщении говорилось, что для зарегистрированного домена
`remotewire.net` уже было выпущено **50 сертификатов за 168 часов**. В
ответе указывалось время повторной попытки:

``` text
2026-10-26 18:39:13 UTC
```

Это было ограничение частоты выпуска сертификатов, а не ошибка самого
reverse proxy и не доказательство неправильной конфигурации IndexD.

Для проверки первоначальной схемы использовался staging ACME Let's
Encrypt:

``` text
https://acme-staging-v02.api.letsencrypt.org/directory
```

Staging предназначен для тестирования и не выдаёт обычный доверенный
браузерами production-сертификат. Поэтому успешная проверка на staging
не завершала задачу с публичным сертификатом.

## 7. Сложность № 2: переход на ZeroSSL

Для дальнейшей настройки выбрали ZeroSSL ACME endpoint:

``` text
https://acme.zerossl.com/v2/DV90
```

ZeroSSL ACME требовал External Account Binding (EAB). Для учётной записи
были доступны: - API Key; - EAB KID; - EAB HMAC Key.

Эти значения используются при регистрации ACME-аккаунта. **Не вставляйте
реальные значения в публичную инструкцию, скриншоты, репозиторий или
логи.** В рабочем окружении их нужно передавать безопасным способом,
поддерживаемым конкретной конфигурацией Caddy.

В логах Caddy версии `v2.11.7` была подтверждена регистрация
ACME-аккаунта ZeroSSL с EAB. Затем началось создание заказа сертификата
(`newOrder`), но один из запросов ожидал HTTP/2 response headers и
завершился тайм-аутом примерно через 30 секунд, после чего Caddy
повторил попытку.

Это промежуточное сообщение само по себе не подтверждало ни
окончательный провал, ни успешный выпуск сертификата. Поэтому проверять
результат следовало по последующим логам и реальному HTTPS-соединению.

## 8. Проверка HTTPS и обратного проксирования

Сначала тестировался ответ самого Caddy:

``` text
indexD HTTPS endpoint is ready
```

Затем выполнялась проверка HTTPS с `curl.exe`. В ходе диагностики
использовался тест с `-k`, например:

``` powershell
curl.exe -k -i https://mainask.remotewire.net:18443/
```

Параметр `-k` отключает проверку доверия к сертификату. Он полезен
только для диагностики TLS-соединения и **не подходит как окончательная
проверка доверенного сертификата**.

После переключения Caddy на обратное проксирование запрос:

``` powershell
curl.exe -i https://mainask.remotewire.net:18443/
```

возвращал HTTP `404` от IndexD. В ходе настройки сертификат ZeroSSL в
итоге проверялся как действительный и доверенный, а запрос к публичному
endpoint доходил до IndexD.

Почему `404` здесь допустим: - TLS-соединение установилось; - запрос
дошёл через Caddy до upstream; - IndexD ответил, что для пути `/` нет
обработчика.

Для окончательной проверки сертификата используйте запрос **без** `-k`:

``` powershell
curl.exe -i https://mainask.remotewire.net:18443/
```

Если проверка сертификата не проходит, не маскируйте это постоянным
использованием `-k`: проверьте имя сертификата, срок действия, цепочку
доверия, системное время и логи Caddy.

## 9. Авторизация S3D и запуск удалённой локации

После настройки публичного endpoint была подготовлена программа S3D в
каталоге:

``` text
C:\S3D
```

### 9.1. Вход

В PowerShell:

``` powershell
Set-Location C:\S3D
.\s3d.exe login
```

Программа выдала URL авторизации. Его открыли в браузере, затем в
интерфейсе IndexD создали новый ключ для подключения и подтвердили
авторизацию.

В успешном случае были получены сообщения:

``` text
Connection approved
```

и в PowerShell:

``` text
Login successful. You can now start s3d
```

Если авторизация не завершилась, проверьте адрес, открытый в браузере,
выбранный ключ и сообщения в консоли. Не публикуйте ключи и токены.

### 9.2. Конфигурация S3D

Конфигурация была найдена в профиле пользователя:

``` text
C:\Users\admin\AppData\Roaming\s3d\
```

Её скопировали в:

``` text
C:\S3D
```

В используемой конфигурации изменили параметры распределения данных:

``` yaml
dataShards: 3
parityShards: 2
```

Это значения конкретной установки, а не универсальная рекомендация.
Перед изменением параметров изучите их смысл и сохраните остальные поля
конфигурации.

### 9.3. Запуск

После успешной авторизации:

``` powershell
Set-Location C:\S3D
.\s3d.exe
```

После запуска нужно убедиться, что процесс остаётся активным, консоль не
показывает ошибок, а состояние локации отображается в интерфейсе IndexD.
Сам факт запуска процесса ещё не доказывает, что все внешние соединения
и операции работают правильно.

## 11. Итоговая схема

В результате настройка была сведена к следующему потоку:

``` text
Внешний клиент
      |
      | HTTPS: mainask.remotewire.net:18443
      v
    Caddy
      |
      | reverse_proxy
      v
IndexD application API
127.0.0.1:19982

S3D на Windows
C:\S3D\s3d.exe
      |
      | авторизация через браузер и ключ IndexD
      v
удалённая локация IndexD
```

Схема показывает архитектурную роль компонентов, но не заменяет проверку
конкретных сетевых правил и конфигурационных файлов.

## 12. Чек-лист для повторения

-   [ ] IndexD запущен, локальный application endpoint определён.
-   [ ] Проверено, какой ответ возвращает локальный endpoint.
-   [ ] Домен `mainask.remotewire.net` настроен на нужный внешний адрес.
-   [ ] Caddy слушает публичный HTTPS-порт `18443`.
-   [ ] Caddy проксирует запросы на `127.0.0.1:19982`.
-   [ ] Настройка ACME соответствует выбранному центру сертификации.
-   [ ] Если используется ZeroSSL ACME, EAB-данные указаны безопасно.
-   [ ] Сертификат проверяется без `curl -k`.
-   [ ] `advertiseURL` указывает на
    `https://mainask.remotewire.net:18443`.
-   [ ] Выполнена авторизация через `.\s3d.exe login`.
-   [ ] Получены `Connection approved` и `Login successful`.
-   [ ] Конфигурация S3D находится в ожидаемом каталоге.
-   [ ] `.\s3d.exe` запущен, ошибки проверены, состояние локации
    проверено в IndexD.
