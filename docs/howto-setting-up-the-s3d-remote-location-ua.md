# Налаштування віддаленої локації IndexD у Windows: від локального запуску до HTTPS

Практичний звіт про налаштування віддаленої локації IndexD у Windows.
Документ описує пройдені етапи: конфігурацію IndexD, домен, Caddy,
отримання TLS-сертифіката, зворотне проксіювання, авторизацію S3D і
запуск локації.

> **Межі інструкції.** Нижче відокремлено підтверджені дії та результати
> від деталей, які не вдалося повністю відновити. Остаточний `Caddyfile`
> і деякі проміжні команди не реконструюються навмання. Секрети
> DNS-провайдера та ZeroSSL не можна публікувати.

## 1. Схема системи

Під час налаштування використовувалися такі адреси й порти:

  ----------------------------------------------------------------------------------------
  Компонент               Адреса / порт                            Призначення
  ----------------------- ---------------------------------------- -----------------------
  Публічне ім'я           `mainask.remotewire.net`                 Домен віддаленої
                                                                   локації

  Публічний HTTPS         `https://mainask.remotewire.net:18443`   Адреса для зовнішніх
  endpoint                                                         підключень

  Caddy                   HTTPS на порту `18443`                   TLS і зворотне
                                                                   проксіювання

  IndexD application API  `127.0.0.1:19982`                        Локальний upstream для
                                                                   Caddy

  IndexD syncer           `127.0.0.1:19981`                        Локальний syncer

  IndexD admin API        `0.0.0.0:19980`                          Admin API, прив'язаний
                                                                   до всіх інтерфейсів

  PostgreSQL              `127.0.0.1:5432`                         Локальна база даних

  Каталог даних           `D:\IndexD\data\`                        Дані IndexD

  Програма S3D            `C:\S3D\s3d.exe`                         Процес віддаленої
                                                                   локації
  ----------------------------------------------------------------------------------------

Ці значення належать конкретному середовищу. Не копіюйте їх без
перевірки. Зокрема, admin API на `0.0.0.0:19980` слухає всі мережеві
інтерфейси --- доступ до нього слід обмежити відповідно до вимог вашої
інсталяції.

## 2. Перевірка локального IndexD перед налаштуванням HTTPS

Локальний application endpoint:

``` text
127.0.0.1:19982
```

Перевірка кореневого URL:

``` powershell
curl.exe -i http://127.0.0.1:19982/
```

**Спостережений результат:** IndexD повертав `404` для `/`. Це саме по
собі не означає, що сервіс не працює: кореневий шлях може не мати
обробника. Пізніше відповідь `404` на публічному HTTPS endpoint також
підтвердила, що запит через Caddy дійшов до IndexD.

Розрізняйте: - відмову з'єднання або тайм-аут --- можлива проблема
доступності, маршруту, порту чи процесу; - HTTP `404` від IndexD ---
з'єднання встановлено, але конкретний шлях `/` не знайдено.

## 3. Конфігурація IndexD

Під час налаштування були зафіксовані такі значення:

``` yaml
applicationAPI: 127.0.0.1:19982
adminAPI: 0.0.0.0:19980
syncer: 127.0.0.1:19981
advertiseURL: https://mainask.remotewire.net:18443
data: d:\IndexD\data\
bootstrap: true
network: mainnet
```

Це перелік параметрів, зафіксованих під час роботи, а не гарантовано
повний конфігураційний файл. Назви полів можуть залежати від версії.
Зберігайте інші обов'язкові параметри й перевіряйте синтаксис за
конфігурацією саме вашої версії.

На початковому етапі `advertiseURL` був локальним:

``` yaml
advertiseURL: http://localhost:19982
```

Після підготовки публічного HTTPS endpoint його змінили на:

``` yaml
advertiseURL: https://mainask.remotewire.net:18443
```

Це дає змогу оголошувати зовнішню адресу, за якою інші учасники мають
звертатися до локації, замість внутрішньої loopback-адреси.

## 4. Домен і DNS

Для публічного endpoint використовувалося ім'я:

``` text
mainask.remotewire.net
```

DNS обслуговувався через Dynu. Домен має вказувати на зовнішню адресу
машини, що приймає підключення, а Caddy повинен мати змогу підтвердити
контроль над доменом під час випуску сертифіката.

Перед повторенням налаштування перевірте: 1. домен розв'язується в
актуальну зовнішню IP-адресу; 2. на маршрутизаторі та/або у Windows
Firewall дозволено вхідний трафік на вибраний публічний порт; 3. Caddy
слухає саме той порт, який указано в публічному URL; 4. якщо
використовується DNS challenge, Caddy має відповідний DNS-провайдер і
дійсні API-дані доступу до Dynu.

Точні DNS-записи, правила маршрутизатора та Windows Firewall у
збереженій історії не зафіксовані, тому тут вони не наводяться як уже
виконані команди.

## 5. Caddy як HTTPS reverse proxy

Caddy використовувався як HTTPS reverse proxy: приймав запити на
публічній адресі й передавав їх локальному IndexD application API.

Публічний endpoint:

``` text
https://mainask.remotewire.net:18443
```

Локальний upstream:

``` text
127.0.0.1:19982
```

Схематичний приклад проксіювання:

``` caddyfile
https://mainask.remotewire.net:18443 {
    # TLS/issuer і DNS challenge мають відповідати
    # встановленій збірці Caddy та конфігурації Dynu.
    reverse_proxy 127.0.0.1:19982
}
```

Це **схематичний фрагмент**, а не повний остаточний `Caddyfile`: повна
конфігурація TLS і DNS-провайдера не збереглася в доступній історії. Не
замінюйте ним робочий файл цілком.

Спочатку використовувався тестовий відгук Caddy:

``` caddyfile
respond "indexD HTTPS endpoint is ready" 200
```

Він давав змогу перевірити HTTPS і маршрут до Caddy окремо від IndexD.
Пізніше тестовий `respond` замінили на `reverse_proxy 127.0.0.1:19982`.

## 6. Складність № 1: обмеження Let's Encrypt

Під час першої спроби отримати сертифікат через production ACME Let's
Encrypt було отримано HTTP `429`.

У повідомленні йшлося, що для зареєстрованого домену `remotewire.net`
уже випустили **50 сертифікатів за 168 годин**. У відповіді було вказано
час повторної спроби:

``` text
2026-10-26 18:39:13 UTC
```

Це було обмеження частоти випуску сертифікатів, а не помилка самого
reverse proxy і не доказ неправильної конфігурації IndexD.

Для перевірки початкової схеми використовувалося staging-середовище ACME
Let's Encrypt:

``` text
https://acme-staging-v02.api.letsencrypt.org/directory
```

Staging призначений для тестування й не видає звичайний
production-сертифікат, якому довіряють браузери. Тому успішна перевірка
в staging не завершувала завдання отримання публічного сертифіката.

## 7. Складність № 2: перехід на ZeroSSL

Для подальшого налаштування вибрали ACME endpoint ZeroSSL:

``` text
https://acme.zerossl.com/v2/DV90
```

ZeroSSL ACME вимагав External Account Binding (EAB). Для облікового
запису були доступні: - API Key; - EAB KID; - EAB HMAC Key.

Ці значення використовуються під час реєстрації ACME-облікового запису.
**Не вставляйте справжні значення в публічну інструкцію, скриншоти,
репозиторій або логи.** Передавайте їх лише безпечним способом, який
підтримує конкретна конфігурація Caddy.

У логах Caddy версії `v2.11.7` було підтверджено реєстрацію
ACME-облікового запису ZeroSSL з EAB. Потім почалося створення
замовлення сертифіката (`newOrder`), але один із запитів очікував HTTP/2
response headers і завершився тайм-аутом приблизно через 30 секунд;
після цього Caddy повторив спробу.

Це проміжне повідомлення саме по собі не підтверджувало ані остаточну
невдачу, ані успішний випуск. Результат потрібно було перевіряти за
наступними логами та реальним HTTPS-з'єднанням.

## 8. Перевірка HTTPS і reverse proxy

Спочатку перевіряли відповідь самого Caddy:

``` text
indexD HTTPS endpoint is ready
```

Під час діагностики використовувався запит `curl.exe` із ключем `-k`,
наприклад:

``` powershell
curl.exe -k -i https://mainask.remotewire.net:18443/
```

Параметр `-k` вимикає перевірку довіри до сертифіката. Він корисний лише
для діагностики TLS-з'єднання й **не підходить для остаточної перевірки
довіреного сертифіката**.

Після перемикання Caddy на reverse proxy запит:

``` powershell
curl.exe -i https://mainask.remotewire.net:18443/
```

повертав HTTP `404` від IndexD. Зрештою сертифікат ZeroSSL перевірили як
чинний і довірений, а запит до публічного endpoint доходив до IndexD.

Чому `404` тут допустимий: - TLS-з'єднання встановилося; - запит пройшов
через Caddy до upstream; - IndexD відповів, що для шляху `/` немає
обробника.

Для остаточної перевірки сертифіката використовуйте запит **без** `-k`:

``` powershell
curl.exe -i https://mainask.remotewire.net:18443/
```

Якщо перевірка сертифіката не проходить, не використовуйте `-k`
постійно. Перевірте ім'я сертифіката, термін дії, ланцюжок довіри,
системний час і логи Caddy.

## 9. Авторизація S3D і запуск віддаленої локації

Програму S3D підготували в каталозі:

``` text
C:\S3D
```

### 9.1. Вхід

У PowerShell:

``` powershell
Set-Location C:\S3D
.\s3d.exe login
```

Програма надала URL авторизації. Його відкрили в браузері, після чого в
інтерфейсі IndexD створили новий ключ для підключення та підтвердили
авторизацію.

Під час успішного входу з'явилися повідомлення:

``` text
Connection approved
```

і в PowerShell:

``` text
Login successful. You can now start s3d
```

Якщо авторизація не завершилася, перевірте адресу в браузері, вибраний
ключ і повідомлення в консолі. Не публікуйте ключі й токени.

### 9.2. Конфігурація S3D

Конфігурацію знайшли в профілі користувача:

``` text
C:\Users\admin\AppData\Roaming\s3d\
```

Її скопіювали до:

``` text
C:\S3D
```

У конфігурації змінили параметри розподілу даних:

``` yaml
dataShards: 3
parityShards: 2
```

Це значення конкретної інсталяції, а не універсальна рекомендація. Перед
зміною параметрів перевірте їхнє призначення та збережіть інші поля
конфігурації.

### 9.3. Запуск

Після успішної авторизації:

``` powershell
Set-Location C:\S3D
.\s3d.exe
```

Переконайтеся, що процес залишається активним, у консолі немає помилок,
а стан локації відображається в інтерфейсі IndexD. Сам факт запуску
процесу ще не доводить, що всі зовнішні з'єднання й операції працюють
належним чином.

## 11. Підсумкова схема

``` text
Зовнішній клієнт
      |
      | HTTPS: mainask.remotewire.net:18443
      v
    Caddy
      |
      | reverse_proxy
      v
IndexD application API
127.0.0.1:19982

S3D у Windows
C:\S3D\s3d.exe
      |
      | авторизація через браузер і ключ IndexD
      v
віддалена локація IndexD
```

Це схема ролей компонентів, а не заміна перевірки реальних мережевих
правил і конфігураційних файлів.

    адресу.
-   [ ] Caddy слухає публічний HTTPS-порт `18443`.
-   [ ] Caddy проксіює запити на `127.0.0.1:19982`.
-   [ ] Налаштування ACME відповідає вибраному центру сертифікації.
-   [ ] Для ZeroSSL ACME EAB-дані задано безпечно.
-   [ ] Сертифікат перевіряється без `curl -k`.
-   [ ] `advertiseURL` указує на `https://mainask.remotewire.net:18443`.
-   [ ] Виконано авторизацію через `.\s3d.exe login`.
-   [ ] Отримано `Connection approved` і `Login successful`.
